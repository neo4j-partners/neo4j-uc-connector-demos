= Aircraft Digital Twin: Dataset Schema
:description: Node types, relationship types, property names, expected row counts, and CSV file inventory for the aircraft digital twin graph used throughout this guide

The aircraft digital twin dataset models a fleet of 20 commercial aircraft operating across 12 airports. The graph connects aircraft maintenance history, flight operations, and sensor topology — this structure is what makes the federated queries throughout this guide possible. When a query joins Neo4j maintenance counts with Delta sensor readings, it is traversing this graph on the Neo4j side and joining on `aircraftId` or `sensorId` on the Delta side.

The `severity` property on `MaintenanceEvent` takes values `CRITICAL`, `WARNING`, and `INFO`. The `minutes` property on `Delay` is an integer. The `iata` property on `Airport` is the join key used when matching flight origin/destination codes to airport nodes.

== Relationship Types

[cols="2,3"]
|===
|Type |Traversal Pattern

|`HAS_SYSTEM`
|`(Aircraft)-[:HAS_SYSTEM]->(System)`

|`HAS_COMPONENT`
|`(System)-[:HAS_COMPONENT]->(Component)`

|`HAS_SENSOR`
|`(System)-[:HAS_SENSOR]->(Sensor)`

|`OPERATES_FLIGHT`
|`(Aircraft)-[:OPERATES_FLIGHT]->(Flight)`

|`DEPARTS_FROM`
|`(Flight)-[:DEPARTS_FROM]->(Airport)`

|`ARRIVES_AT`
|`(Flight)-[:ARRIVES_AT]->(Airport)`

|`HAS_DELAY`
|`(Flight)-[:HAS_DELAY]->(Delay)`

|`HAS_EVENT`
|`(Component)-[:HAS_EVENT]->(MaintenanceEvent)`

|===

In the JDBC SQL-to-Cypher translator, relationship types become the middle "table" in a `NATURAL JOIN`. The query `FROM Flight f NATURAL JOIN DEPARTS_FROM r NATURAL JOIN Airport a` translates to the Cypher pattern `(f:Flight)-[:DEPARTS_FROM]->(a:Airport)`.

== Delta Table: sensor_readings

Sensor time-series data is not stored in Neo4j. It lives as a Delta table in the Unity Catalog schema alongside the materialized graph tables and is the primary join target in the federated analytics queries.

[cols="2,1,4"]
|===
|Column |Type |Description

|`readingId`
|STRING
|Unique identifier for the reading

|`sensorId`
|STRING
|Foreign key matching `Sensor.sensorId` in the graph

|`ts`
|TIMESTAMP
|Reading timestamp

|`value`
|DOUBLE
|Sensor measurement in the sensor's native unit

|===

Expected row count: 172,800 (160 sensors × 1,080 readings each). Notebook `01-neo4j-uc-connection-setup.ipynb` loads this table from `nodes_readings.csv` with `read_files()`, normalizes the raw CSV headers to camelCase, and writes it directly into Delta. It does not pass through Neo4j.

== Indexes

The graph loader creates one index per node type on its primary key property:

[source,cypher]
----
CREATE INDEX aircraftId IF NOT EXISTS FOR (n:Aircraft) ON (n.aircraftId)
CREATE INDEX airport_id  IF NOT EXISTS FOR (n:Airport)  ON (n.airportId)
CREATE INDEX systemId   IF NOT EXISTS FOR (n:System)   ON (n.systemId)
CREATE INDEX component_id IF NOT EXISTS FOR (n:Component) ON (n.componentId)
CREATE INDEX sensorId   IF NOT EXISTS FOR (n:Sensor)   ON (n.sensorId)
CREATE INDEX flight_id   IF NOT EXISTS FOR (n:Flight)   ON (n.flightId)
CREATE INDEX delay_id    IF NOT EXISTS FOR (n:Delay)    ON (n.delayId)
CREATE INDEX maint_id    IF NOT EXISTS FOR (n:MaintenanceEvent) ON (n.eventId)
----

These indexes support the `MATCH` lookups in the relationship loading queries, where each edge CSV row is resolved to its start and end nodes by primary key.

== CSV File Inventory

The dataset ships as 17 CSV files uploaded to a UC Volume by `getting-started/upload_data.sh`. Node files follow Neo4j import format: the primary key column header is `:ID(Label)`, relationship source is `:START_ID(Label)`, and target is `:END_ID(Label)`. The `data_utils.csv_rows()` function normalizes these headers to `id`, `start_id`, and `end_id` before passing rows to Cypher.
