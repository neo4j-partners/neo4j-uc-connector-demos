= Delta Materialization: Copying Neo4j Graph Data into Unity Catalog
:description: Pattern for materializing Neo4j node types as Delta tables, enabling Genie, AI/BI dashboards, and SQL analytics without per-query JDBC overhead

Single-statement federation via `remote_query()` works well for aggregate queries that run on demand. But some tools, such as Genie Spaces, AI/BI dashboards, and general-purpose SQL notebooks, expect Delta tables, not federated JDBC connections. Materialization solves this by reading all Neo4j node types once through `remote_query()` and writing them as Delta tables in the Unity Catalog schema. Once materialized, these tables join with the `sensor_readings` Delta table using standard Spark SQL, with no `remote_query()` call, JDBC round-trip, or translator limitation per query.

== When to Materialize

Materialization makes sense when:

* **Genie** needs access to Neo4j graph topology. Genie queries Delta tables; it cannot issue JDBC queries directly.
* **AI/BI dashboards** need stable, cacheable data from the graph.
* **SQL notebooks or analysts** need to join graph topology with sensor data repeatedly, and the per-query JDBC overhead is measurable.
* The graph data is not updated frequently enough to make staleness a concern.

For freshness-sensitive queries or exploratory one-off analysis, `remote_query()` or the PySpark DataFrame API are better choices. For a comparison of all three approaches, see xref:uc-integration-setup.adoc#choosing-the-right-method[Choosing the Right Method].

== The Materialization Pattern

Each node type follows the same sequence: read from Neo4j via `remote_query()`, cast all columns to `STRING` for a stable Delta-friendly schema across runs, then write as a Delta table with `overwriteSchema`:

[source,python]
----
from pyspark.sql.types import StringType

def materialize(table_name, query, expected_count):
    df = spark.sql(f"""
        SELECT * FROM remote_query('neo4j_connection',
            query => '{query}'
        )
    """)

    # Cast all columns to STRING for a stable, Delta-friendly schema across runs
    for col_name in df.columns:
        df = df.withColumn(col_name, df[col_name].cast(StringType()))

    df.write.format("delta") \
        .mode("overwrite") \
        .option("overwriteSchema", "true") \
        .saveAsTable(f"{schema}.{table_name}")
----

The STRING cast normalizes column types so the Delta write is robust regardless of how `remote_query()` infers types from the JDBC result.

== Node Tables

The following tables materialize all eight node types. Once written, each table is queryable as a standard Delta table with no JDBC dependency.

[source,python]
----
materialize("neo4j_aircraft",
    query="SELECT aircraftId, tail_number, icao24, model, manufacturer, operator FROM Aircraft",
    expected_count=20)

materialize("neo4j_airports",
    query="SELECT airportId, name, city, country, iata, icao FROM Airport",
    expected_count=12)

materialize("neo4j_systems",
    query="SELECT systemId, aircraftId, type, name FROM System",
    expected_count=80)

materialize("neo4j_sensors",
    query="SELECT sensorId, systemId, type, name, unit FROM Sensor",
    expected_count=160)

materialize("neo4j_components",
    query="SELECT componentId, systemId, type, name FROM Component",
    expected_count=320)

materialize("neo4j_maintenance_events",
    query="SELECT eventId, componentId, systemId, aircraftId, fault, severity, reported_at, corrective_action FROM MaintenanceEvent",
    expected_count=300)

materialize("neo4j_flights",
    query="SELECT flightId, flight_number, aircraftId, operator, origin, destination, scheduled_departure, scheduled_arrival FROM Flight",
    expected_count=800)

materialize("neo4j_delays",
    query="SELECT delayId, flightId, cause, CAST(minutes AS STRING) AS minutes FROM Delay",
    expected_count=514)
----

== Relationship Table via NATURAL JOIN

The aircraft-to-system relationship table is materialized by calling `remote_query()` with a `NATURAL JOIN`. The Neo4j JDBC translator rewrites that into a Cypher `MATCH (a:Aircraft)-[:HAS_SYSTEM]->(s:System)` traversal on the Neo4j side:

[source,python]
----
df = spark.sql(f"""
    SELECT aircraftId, model, systemId, systemType, systemName
    FROM remote_query('neo4j_connection',
        query => 'SELECT a.aircraftId AS aircraftId,
                         a.model AS model,
                         s.systemId AS systemId,
                         s.type AS systemType,
                         s.name AS systemName,
                         COUNT(*) AS cnt
                  FROM Aircraft a NATURAL JOIN HAS_SYSTEM rel NATURAL JOIN System s
                  GROUP BY a.aircraftId, a.model, s.systemId, s.type, s.name
                  HAVING COUNT(*) > 0'
    )
""")

for col_name in df.columns:
    df = df.withColumn(col_name, df[col_name].cast(StringType()))

df.write.format("delta") \
    .mode("overwrite") \
    .option("overwriteSchema", "true") \
    .saveAsTable(f"{schema}.neo4j_aircraft_systems")
----

The `HAVING COUNT(*) > 0` clause is a semantic no-op that works around a Databricks `remote_query()` caching quirk for pure `GROUP BY` queries on warm clusters. See xref:troubleshooting.adoc[Troubleshooting].

Expected row count: 80 (one row per Aircraft-System pair, matching the 80 System nodes).

== Querying Materialized Tables

Once all node tables exist in the Unity Catalog schema, they join with `sensor_readings` through standard Spark SQL. No JDBC connection is needed at query time:

[source,sql]
----
-- Sensor health by aircraft system type
SELECT sys.type AS system_type,
       COUNT(DISTINCT s.sensorId) AS sensor_count,
       COUNT(r.readingId)        AS total_readings,
       ROUND(AVG(r.value), 2)     AS avg_reading,
       ROUND(STDDEV(r.value), 2)  AS stddev_reading
FROM neo4j_sensors s
JOIN neo4j_systems sys  ON s.systemId  = sys.systemId
JOIN sensor_readings r  ON r.sensorId = s.sensorId
GROUP BY sys.type
ORDER BY total_readings DESC
----

[source,sql]
----
-- Busiest airport pairs by flight volume
SELECT dep.city AS origin_city, dep.iata AS origin,
       arr.city AS destination_city, arr.iata AS destination,
       COUNT(*) AS flight_count
FROM neo4j_flights f
JOIN neo4j_airports dep ON f.origin      = dep.iata
JOIN neo4j_airports arr ON f.destination = arr.iata
GROUP BY dep.city, dep.iata, arr.city, arr.iata
ORDER BY flight_count DESC
LIMIT 10
----

[source,sql]
----
-- Aircraft health: maintenance events and sensor averages side by side
SELECT a.aircraftId, a.model, a.operator,
       COUNT(DISTINCT m.eventId) AS maintenance_events,
       SUM(CASE WHEN m.severity = 'CRITICAL' THEN 1 ELSE 0 END) AS critical_events,
       ROUND(AVG(r.value), 2) AS avg_sensor_reading
FROM neo4j_aircraft a
LEFT JOIN neo4j_maintenance_events m ON a.aircraftId = m.aircraftId
LEFT JOIN neo4j_sensors s            ON s.systemId   IN (
    SELECT systemId FROM neo4j_systems WHERE aircraftId = a.aircraftId
)
LEFT JOIN sensor_readings r ON r.sensorId = s.sensorId
GROUP BY a.aircraftId, a.model, a.operator
ORDER BY critical_events DESC
----

NOTE: Materialized tables reflect a point-in-time snapshot of the Neo4j graph. Re-run the materialization to pick up changes in the graph. For applications that need near-real-time graph data, use `remote_query()` or the PySpark DataFrame API instead.
